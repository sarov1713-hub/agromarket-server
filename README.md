# АгроМаркет API

[![CI](https://github.com/sarov1713-hub/agromarket-server/actions/workflows/ci.yml/badge.svg)](https://github.com/sarov1713-hub/agromarket-server/actions/workflows/ci.yml)

Backend лабораторных №6–8: Express 5, PostgreSQL, параметризованные SQL-запросы.
Это отдельный npm- и Git-проект внутри frontend. React поддерживает регистрацию, вход и добавление товаров администратором.

## Запуск

Для текущего компьютера база `agromarket` на DB01 уже создана, а рабочий
`DATABASE_URL` находится в `.env`. Повторно создавать базу или менять пароль не нужно.

```powershell
cd D:\agromarket-react\agromarket-server
npm install
npm run dev
```

API: http://localhost:3000. Проверка подключения: http://localhost:3000/api/health.
Ожидается JSON с `status: "ok"`, `db: "connected"` и `time`.

На новом компьютере: обеспечить доступ к PostgreSQL, создать базу `agromarket`,
скопировать [.env.example](./.env.example) в `.env` и указать рабочий `DATABASE_URL`.
Не перезаписывать уже настроенный `.env` примером.

Первичная инициализация (в текущей базе уже выполнена):

```powershell
npm run db:init
```

**Повторный `db:init` удаляет таблицы orders, products и users со всеми данными**, затем
создаёт их заново, создаёт администратора из переменных окружения и загружает четыре товара из [data/db.json](./data/db.json).
Все действия выполняются в транзакции: при ошибке изменения откатываются.
SERIAL выдаёт идентификаторы; единица товара берётся из окончания названия (`л`/`кг`).
Не запускать эту команду для обычного перезапуска сервера.

Frontend в другом терминале:

```powershell
cd D:\agromarket-react
npm run dev
```

Открыть http://localhost:5173. `CORS_ORIGIN` задаёт разрешённый origin, по умолчанию
это `http://localhost:5173`. `PORT` по умолчанию равен 3000. Для запуска без watch: `npm start`.

## Эндпоинты

| Метод | Путь | Доступ | Ответы |
|---|---|---|---|
| GET | /api/health | Все | 200, 500 |
| GET | /api/about | Все | 200 |
| GET | /api/products?search=мол | Все | 200, 400 |
| GET | /api/products/:id | Все | 200, 400, 404 |
| POST | /api/auth/register | Все | 201, 400, 409 |
| POST | /api/auth/login | Все | 200, 400, 401, 429 |
| GET | /api/auth/me | Bearer token | 200, 401, 404 |
| POST | /api/products | admin | 201, 400, 401, 403 |
| PUT | /api/products/:id | admin | 200, 400, 401, 403, 404 |
| DELETE | /api/products/:id | admin | 204, 400, 401, 403, 404 |
| GET | /api/orders | admin | 200, 401, 403 |
| POST | /api/orders | Все | 201, 400 |
| PATCH | /api/orders/:id | admin | 200, 400, 401, 403, 404 |

Неизвестные маршруты возвращают 404 JSON. Неожиданные ошибки и недоступность БД —
500 JSON без технических деталей. Некорректный JSON — 400, слишком большое тело — 413.

Товар: обязательны непустой `name` и целый `price >= 0` в диапазоне PostgreSQL INTEGER.
Необязательные поля: `category`, `image`, `unit` (по умолчанию `кг`).
PUT заменяет все редактируемые поля: пропущенные `category`/`image` становятся null,
`unit` — `кг`. Поля `id` и `created_at` сохраняются.

Заявка: обязательны `name`, `email`, целый `quantity >= 10`.
Принимаются также `product_id`, `phone`, `date`, `comment`.
Поле формы `date` сохраняется в `delivery_date` и возвращается строкой YYYY-MM-DD.
Пустые необязательные значения сохраняются как null. Статус при создании — `new`.
PATCH принимает `{ "status": "processing" }`. Допустимые статусы контролирует CHECK:
`new`, `processing`, `done`, `cancelled`.

## Авторизация ЛР7

Регистрация принимает name, email, password. Email нормализуется trim + lowercase,
пароль — минимум 8 символов, максимум 72 байта (ограничение bcrypt).
Роль всегда user, даже если клиент присылает role=admin. Пароли хранятся как
bcrypt hash с cost 10. JWT содержит sub и role, а также стандартные iat/exp.
В ответах register/login/me нет password_hash.

Для защищённых запросов используется Authorization: Bearer <token>.
POST/PUT/DELETE products и GET/PATCH orders доступны только admin.
POST orders остаётся публичным; user_id добавлен в схему, но для публичных заявок
остаётся null. Бонусный optionalAuth не реализован.

Login: пять неуспешных запросов за 15 минут на IP, следующий возвращает 429.
Успешные входы не учитываются. Счётчик хранится в памяти и сбрасывается при
перезапуске Express. RateLimit и Retry-After позволяют узнать состояние ограничения.
Helmet включён перед CORS; JSON ограничен 10kb. Ошибки JSON возвращаются как JSON.

Frontend хранит только token и безопасный user в localStorage. При запуске проверяет
/auth/me. При 401 с сохранённым токеном очищает оба значения и перезагружает страницу.
Logout также очищает их. localStorage выбран по заданию; его доступность JavaScript
означает, что защита от XSS важна. Скрытие формы администратора дополняет серверные права.

Postman использует Bearer {{token}} на уровне коллекции. Сразу после Health выполняется
вход администратора. Регистрация и вход имеют No Auth, user-проверки используют
{{userToken}}. В коллекции указан учебный пароль из задания; это не JWT_SECRET.
Если ADMIN_PASSWORD изменён, обновить локальное значение adminPassword в Postman.
Email регистрации содержит timestamp и guid, поэтому повторный прогон не конфликтует.

## Тестирование

Рабочая база — agromarket, тестовая — **agromarket_test**.
Все команды выполняются из отдельного backend-репозитория.

1. Создать agromarket_test на PostgreSQL (в текущем окружении уже создана).
   Для Windows-хоста должен быть разрешён доступ именно к этой базе в pg_hba.conf.
2. Создать локальный .env.test на основе .env, сохранив параметры подключения,
   но заменив имя базы в DATABASE_URL на agromarket_test. Не публиковать строку подключения.
   Задать NODE_ENV=test, отдельный тестовый JWT_SECRET, JWT_EXPIRES_IN=2h,
   ADMIN_EMAIL, ADMIN_PASSWORD и CORS_ORIGIN=http://localhost:5173.
3. Установить зависимости: `npm ci`.
4. Выполнить `npm test`.
5. Для наблюдения за изменениями: `npm run test:watch`; выход — q или Ctrl+C.
6. Покрытие: `npm run coverage`. HTML-отчёт: [coverage/index.html](./coverage/index.html).

Конфигурация загружает .env.test с override; при отсутствии файла локальный запуск
завершается ошибкой, к рабочему .env не переходит. В GitHub Actions файл не нужен:
используются job env и отдельный PostgreSQL 16 service.

До запуска db:init globalSetup проверяет строку подключения. Защита проверяет точное
имя agromarket_test, а не только вхождение test: имя хоста или пароль со словом test
не разрешают сброс рабочей базы. URL с параметрами переопределения базы отклоняется.
Та же защита стоит перед созданием Pool при NODE_ENV=test, а seed дополнительно
проверяет SELECT current_database() перед DDL.

**Каждый новый запуск Vitest пересоздаёт только тестовую БД.** Рабочая база не используется.
В tests/ пять файлов: health, products, auth, access, middleware. Уникальные email
исключают конфликты; CRUD-сценарий создаёт собственный товар. fileParallelism=false,
изолированные forks и afterAll(pool.end) закрывают подключения каждого файла.
Unit-тесты middleware используют vi.fn и не выполняют SQL или HTTP-запросов;
общий интеграционный запуск при этом сначала готовит тестовую базу.

Первый замер был 84,21%: по отчёту добавлена проверка неверного типа category.

## Правила работы с Git

- main всегда рабочая; разработка в feature/... или fix/....
- Изменения попадают в main через PR, зелёный CI и review.
- Conventional Commits: feat, fix, test, refactor, docs, ci, chore.
- Backend и frontend — отдельные репозитории и отдельные коммиты/PR.
- .env, .env.test, coverage/ и node_modules/ не коммитятся.
- Workflow CI запускается для pull_request и push в main. Один push feature-ветки
  без PR не запускает этот workflow; до создания PR зелёный CI на GitHub не заявляется.

Backend PR: base main, compare feature/api-tests,
название: `test: API tests, test database and CI`.
Frontend PR: base main, compare feature/env-config,
название: `feat: read API_URL from VITE_API_URL`.

В GitHub вручную: Pull requests → New pull request → выбрать base/compare →
заполнить шаблон → Create pull request. Дождаться CI, пригласить напарника на review.
Не выполнять merge до завершения review.

Branch protection: Settings → Branches → Add branch protection rule → main.
Включить Require a pull request before merging, Require approvals (1),
Require status checks to pass (выбрать job test после первого запуска CI).
Не разрешать force pushes и удаление защищённой ветки. Проверить, распространяется ли
правило на владельца репозитория, прежде чем демонстрировать запрет прямого push.

С напарником: оставить два содержательных комментария и suggestion в его PR,
после исправлений выполнить Approve; получить его review своего PR, исправить замечания.
Эксперимент прямого push в protected main и Squash and merge проводить самостоятельно
в GitHub после настройки защиты. Эти действия агентом не выполняются.

## Безопасность

ЛР11, проверено 06.11.2026. Реальный backend находится в agromarket-server, отдельного agromarket-api нет.

- Helmet подключён до маршрутов: X-Powered-By отсутствует, nosniff и HSTS включены.
- CORS_ORIGINS — список точных origin через запятую. Локально http://localhost:5173; для production добавить https://agromarket-react.vercel.app. Старое CORS_ORIGIN поддерживается, пока новое имя не задано. Запросы без Origin разрешены; чужим origin не выдаётся разрешающий заголовок. Примеры — [.env.example](.env.example).
- Общий IP-лимит login/register: 10 запросов за 15 минут, включая успешные. HTTP 429, сообщение «Слишком много попыток. Попробуйте через 15 минут», RateLimit draft-7 и Retry-After. При NODE_ENV=test выключен. MemoryStore действует в одном процессе и сбрасывается при рестарте; для нескольких инстансов требуется общее хранилище.
- На Render (RENDER=true) trust proxy=1, локально false. Подмена X-Forwarded-For при прямом локальном соединении не обходит лимит. Реальная цепочка Render после нового deploy **не проверена**: один доверенный proxy должен корректно перезаписывать/дополнять XFF, прямого обходного пути к Node быть не должно. См. [Express behind proxies](https://expressjs.com/en/guide/behind-proxies/).
- Zod проверяет register/login и создание/PUT/PATCH товара. safeParse возвращает 400 с error и details[{field,message}], обработчик получает очищенные данные.
- Имя пользователя 2–100, email валидируется и приводится к lowercase; пароль регистрации 8–72 символа и максимум 72 байта UTF-8, входа 1–72. Неизвестные поля, включая role, удаляются. INSERT users не содержит role; БД сохраняет user по умолчанию.
- Товар: name 2–200, category 1–50, price целое >0 и ≤10 000 000 (совместимость с INTEGER), unit 1–20, image до 2048 символов, HTTP(S) либо путь от /. Пустые строки, null, boolean и массивы не превращаются в допустимую цену. PATCH частичный, пустой объект и только неизвестные поля запрещены. PUT сохраняет прежний смысл полной замены.
- ID — положительное десятичное целое в пределах PostgreSQL INTEGER. Некорректный ID даёт 400 до SQL; отсутствующий корректный — 404. Проверены все существующие /:id маршруты товаров и заявок.
- JSON ограничен 100 KB. 20 KB проходит парсер, 101 KB даёт 413.
- React показывает details списком возле формы и сохраняет сообщение 429. Валидация браузера не заменяет серверную.
